========================================
1. PROJECT CONTEXT
========================================

The Empathetic Full-Duplex Speech Language Model (EFSM) project fine-tunes the
Thinker/language backbone of Qwen2.5-style models for empathetic therapeutic
conversation. Because loading the full Qwen2.5-Omni model for training was too
heavy for free GPU environments, the practical training target was changed to
Qwen/Qwen2.5-7B-Instruct, which is treated as the text Thinker-equivalent.

The fine-tuning method is QLoRA:
- Base model: Qwen/Qwen2.5-7B-Instruct
- Adapter repo: tasbid001/efsm-checkpoints-fixed
- Dataset: facebook/empathetic_dialogues
- Training objective: assistant-response-only supervised fine-tuning
- Hardware: Kaggle/Colab free GPU sessions

========================================
2. INITIAL TRAINING RESULT AND THE MAJOR ISSUE FOUND
========================================

The first long training run reached checkpoint-2200 and showed extremely tiny
training/evaluation losses:
- train loss around 1e-5
- eval loss around 4e-5

At first glance this looked like either excellent convergence or overfitting.
After investigation, it was found to be worse than normal overfitting: the
processed dataset itself was wrong.

Root cause:
src/data/preprocess_empathetic.py was using:
  row["prompt"]
as the dialogue turn text.

In EmpatheticDialogues, "prompt" is the situation/context prompt, not the actual
conversation utterance. The actual spoken dialogue turn is:
  row["utterance"]

As a result, many user and assistant messages became exact copies of the same
prompt. The model was not learning empathy; it was learning an artificially easy
copy-style task. This explained the near-zero loss. It was not a trustworthy
fine-tuned model.

Evidence:
The old preprocessing notebook showed examples like:
  USER:      [emotion: embarrassed] I can't believe I actually went to work...
  ASSISTANT: I can't believe I actually went to work...

This invalidated checkpoint-2200 and all earlier checkpoints trained on the
broken JSONL files.

========================================
3. FIXES APPLIED TO DATA PREPROCESSING
========================================

The preprocessing script was fixed:
- Changed dialogue text source from row["prompt"] to row["utterance"]
- Added cleanup for EmpatheticDialogues placeholders such as "_comma_"
- Added a leakage validation check to fail fast if too many assistant turns
  exactly copy the previous user turn

New validator added:
  src/data/validate_jsonl.py

This script checks train/val/test JSONL files and reports:
- number of conversations
- number of assistant turns
- empty turns
- exact user-copy rate

After regenerating JSONL files, the validation results were:
- train exact user copies: 11 / 29278 = 0.04%
- val exact user copies: 0 / 3670 = 0.00%
- test exact user copies: 1 / 3681 = 0.03%

These values are acceptable because tiny exact-copy rates can naturally occur in
dialogue. The major copy-target bug was fixed.

New HuggingFace repo created for clean fixed-data run:
  tasbid001/efsm-checkpoints-fixed

Old checkpoints were not used.

========================================
5. EVALUATION WORK AND CUDA MEMORY ISSUES
========================================

A quick evaluation script/notebook was created:
- src/eval/quick_compare.py
- notebooks/03_quick_evaluate.ipynb
- notebooks/03_quick_evaluate_colab.ipynb

Goal:
Generate a side-by-side table:
  prompt | base_response | fine_tuned_response

Initial evaluation approach:
- Load base model
- Generate base responses
- Unload base model
- Load base model + LoRA adapter
- Generate fine-tuned responses

Problem:
This repeatedly caused CUDA out-of-memory errors on Kaggle T4 GPUs.

Observed behavior:
- GPU 0 filled to around 14.5 GB
- generation requested a small additional allocation
- GPU 1 often stayed at 0% utilization
- reducing prompt count and max_new_tokens did not fix the root issue

PyTorch CUDA memory management was consulted. Allocator settings such as:
  expandable_segments:True
  max_split_size_mb:64
  garbage_collection_threshold:0.8
were added. These help fragmentation and allocator behavior, but the real issue
was that the model/generation workload was too tightly packed onto one T4.

Several fixes were attempted:
- reduce max_new_tokens
- reduce prompt limit
- device_map="auto"
- explicit two-GPU layer split
- CPU offload for later layers

The CPU-offload fallback avoided immediate OOM but was too slow/stalled in
Kaggle for practical use.

========================================
6. FINAL EVALUATION IMPROVEMENT
========================================

The evaluation strategy was changed to a much more memory-efficient approach:
load ONE PEFT model only:
  base Qwen2.5-7B-Instruct + LoRA adapter

Then:
- generate base response with adapter temporarily disabled
- generate fine-tuned response with adapter enabled

This avoids loading two separate 7B models. The new mode is:
  --compare-mode single_peft

The Colab notebook uses:
  --device-strategy single_gpu_4bit
  --compare-mode single_peft

This successfully ran in Colab and produced comparison output.

Qualitative 1-epoch result:
The base model often produced warmer and deeper therapeutic responses than the
1-epoch fine-tuned adapter. The fine-tuned adapter was shorter and more
dataset-like, likely because EmpatheticDialogues contains many short casual
supporter replies.

Conclusion:
The 1-epoch model is a valid recovered checkpoint, but not the final target now
that the deadline is extended. Continue training to 3 epochs and re-evaluate.
